# Decisions

Recorded 30 September 2026 from the project conversation. Items 11 onward include the plan audit and subsequent mockup feedback the same day. Items 29 onward were recorded on 1 October 2026.

Project name: Bukno, pronounced “Buck-no”. License: Apache 2.0, superseding the earlier noncommercial proposal. Commercial use is allowed.

## Agreed

1. Build a lightweight native interface, with Rust as the implementation direction.
2. Use Codex app-server as the Codex agent backend and the preferred starting integration for voice/dictation. Speech remains an integration target, not a verified capability for every login route. The desktop app also has speech networking outside app-server; see the [speech findings](research/README.md#speech-follow-up).
3. Use Claude Agent SDK with the installed Claude Code executable as the second agent backend.
4. Share one composer, project list, conversation interface, and review workflow; retain provider-specific sessions and capabilities.
5. Dictation supplies an editable draft for either provider. Do not build a separate Claude voice service.
6. Plan for an open-source release with Bukno's own Sign in with ChatGPT client for Codex. That client is a public-release item; the daily driver uses the existing Codex login (item 14).
7. Measure the actual process family and the same workload before making memory-saving claims.
8. Support both macOS and Windows. The original requirement to finish both during the first compatibility milestone is superseded by item 30: Mac daily driver first, Windows before public release.
9. Neither dictation nor live voice is required for day one. Ship the first usable release with text workflows for both providers; add both speech features through Codex app-server afterward. This supersedes the earlier reply that dictation should block release.
10. Design for subagent delegation across providers from the start: a Codex or Claude parent can assign a task to a Codex/OpenAI or Claude worker. Bukno owns task relationships, context handoff, lifecycle, and result routing. The exact tool mechanism and delivery milestone are not yet selected.
11. Release path: Bukno starts as Rasmus's daily driver and is published as open source for others to use. Signing, installers, and Bukno's own ChatGPT login follow once the daily text flow is dependable.
12. Claude integration follows the T3 Code approach: the Agent SDK runs and controls the user's installed, signed-in Claude Code CLI. Users sign in through Claude Code itself; Bukno never stores or handles Claude credentials. API-key use is an optional, explicit setting and never an automatic fallback.
13. The interface is native Rust. Webview shells such as Tauri or Electron are out, because low memory use is a core goal. Try egui first in a time-boxed spike. If egui fails a must-have from the [UI contract](implementation-plan.md#2-platform-and-ui-contract), switch to another native Rust toolkit instead of working around it. GPUI, the framework behind Zed, is the first fallback candidate. A consistent custom look is acceptable; native OS widgets are not required.
14. For the daily driver, Bukno starts its own `codex app-server` child process over stdio, using the existing Codex CLI login. It does not attach to the shared `codex app-server daemon`, so Bukno owns and can clean up everything it starts.
15. Engine versions: Bukno uses the installed Codex and Claude Code engines. Codex protocol types are generated from a tested engine's schema. The tested-range gate and “unsupported version” block are superseded by item 32.
16. Claude bridge: a small TypeScript bridge on the Agent SDK, built as one self-contained executable so the packaged app does not depend on a developer Node install. Choose the build tool (Node single executable or Bun compile) during milestone 1.
17. Build a thin working version on macOS with Codex, then Claude. The original Windows-before-daily-driver order is superseded by item 30. Keep early Windows build and native UI checks; finish Windows provider integration after the Mac daily driver.
18. Projectless chats are required for the first usable release. Each has a persistent Bukno-managed workspace even without an attached project or Git repository. Each chat gets an isolated directory. Where those directories live is set by item 33.
19. Develop the selected dark mockup: retain the left navigation and right delegated-work panel, use light blue for Codex and warm orange for Claude, and show assignments and current activity in the right panel. Remove its touched-file list and redundant lower update panel. Keep changed-line totals in a compact expandable strip above the composer; an embedded diff viewer is not required for version one.
20. The chat renders ordinary text, Markdown, tables, and code inline. Full artifact and web previews open in the user's browser for version one, superseding the earlier inline preview card. Working states combine restrained motion with real tool activity and provider-exposed reasoning summaries. The bottom-left profile opens settings and shows a cached usage-limit snapshot with conservative refresh behavior. The [interface specification](implementation-plan.md#interface-direction-from-the-mockup-review) defines the proposed details; mockup usage values are illustrative.
21. Sidebar conversation rows use the title and a small provider logo on the right to identify the chat's owning provider. Remove the chat-bubble icons and the one-sided selection border. A subtle selected-row fill is the proposed replacement; retain a distinct keyboard focus state.
22. Updated after the composer-reference review: the compact model control shows one provider-colored lightning symbol, selected model, quieter reasoning label, and one chevron. No provider logo appears inside the composer; provider identity is already shown elsewhere. The picker uses a stepped effort slider with dim-to-bright blue or orange and a restrained animated treatment at the highest supported levels. Actual effort levels and fast-mode availability come from the selected engine/model; the UI must not invent matching capabilities across providers.
23. Clicking a delegated task opens that task in the main chat view. The user can send follow-ups through its composer. Preserve the parent relationship, separate drafts, and clear recipient identity; communicate additional child work and revised results to the parent.
24. Use the user's browser, such as Chrome, for previews rather than embedding a browser or artifact-preview surface in version one. Keep external opening explicit and browser choice configurable. An embedded browser can be reconsidered later against the native UI and memory goals.
25. Rasmus intends Claude to implement the final animations later. Current imagery is a motion direction only; no animation implementation or worker handoff has been started. Keep reduced motion and measured idle/active rendering cost in the implementation brief.
26. Interface feel is a first-release quality requirement. Prefer spacing, font weight, text color, and subtle surface contrast over ornamental borders. Use restrained shadows for elevation, especially the composer and floating controls. Remove the preview completely from the current chat mockup without replacing it with another panel or placeholder. Preserve clear interactive states and keyboard focus, and verify the visual treatment in the native renderer on both platforms.
27. Use warm grey and charcoal for the application surfaces, without blue undertones. Blue and orange remain provider accents. Follow the supplied ChatGPT composer reference for compact control grouping: tightly grouped lightning/model/effort/chevron, with the model group toward the right. Move the composer and the profile/usage block closer to the window's bottom edge. Preserve the rest of the selected layout.
28. Save the revised mockup and reference for Rasmus's next Claude design-system and screen-story pass before app implementation. That pass should establish consistent tokens, components, states, motion, and different screens. It has not been dispatched or completed in this review.
29. Recorded 1 October 2026: the Claude design pass is approved as the first-version design. Build the interface from [design/README.md](design/README.md): the design system rules and tokens, and the 15-screen user journey. It refines items 19 to 27. The chat holds only the conversation, and while an agent works it ends with a small, slow dotted orb and one line of activity. The agent's to-do list sits in the right panel below Delegated work. The model control opens on reasoning effort with a thick stepped slider, and the model name opens a list with two sections, ChatGPT models (Codex) and Claude models (Claude Code). The repository copy is canonical; the Claude Design artifacts are the editing workspace and are copied back here after changes. Provider marks, model names and example data in the screens are placeholders.
30. Recorded 1 October 2026 from the later design-system discussion: start with the Mac daily driver to reach usable work sooner, while keeping Windows as a public-release requirement. Share the interface, storage, coordination, and provider logic. Isolate executable discovery, paths, process cleanup, window controls, and other OS behavior. Add Windows compilation and an early native UI smoke check; perform full Windows build and authenticated provider testing on a Windows machine after the Mac workflow is dependable. This supersedes the release timing in items 8 and 17, not the two-platform commitment.
31. Recorded 1 October 2026: the [first version specification](first-version-specification.md) is approved as the build plan, with the review changes made the same day. The coordinator is one state machine with an outbox. Bukno's own transcript items are the single display store, with provider history used only for reconciliation and detecting outside continuation. Each section states the pass it lands in. Each provider publishes its own permission presets instead of shared labels. Read-only runs take no writer lease, and a second writer gets Queue or Run anyway instead of a hard block. One Claude bridge serves all Claude chats. The transcript is one custom widget and is built first. The specification is the single source for build order and contracts; the other planning documents defer to it.
32. Recorded 1 October 2026: Bukno works with whatever Codex and Claude Code version is installed, with no version gate. It records the last working version of each engine. If a new version breaks Bukno, the user can switch back to the last working version in one click, and Bukno stays on it until the user chooses to try the latest again. Bukno never changes an engine version without a click. This supersedes the tested-range gate in item 15. Details are in [section 9a of the specification](first-version-specification.md#9a-engine-versions-and-reverting).
33. Recorded 1 October 2026: the app and its runtime state (database, settings, diagnostics) live on the computer's internal drive for speed and so Bukno always opens. During onboarding the user chooses the work folder for projectless chats, attachments, and outputs, which is also the default location offered for projects. Rasmus will choose a folder on Toshiba. This replaces the earlier single Bukno data root on Toshiba.
34. Recorded 1 October 2026: when building starts, Claude does the initial scaffolding and interface setup, including Pass 0 and the native component foundation. Sol (gpt-5.6-sol through Codex) then reviews the code and evidence at each pass boundary. Rasmus decides who implements each later pass.
35. Recorded 1 October 2026: the working indicator is the activity words with a soft light passing through them (`StreakLabel`), at 10 frames a second in the native app. It replaces the `ThinkingOrb` from item 29, which cost about 5 % of a CPU core because egui redraws the whole window for every animation frame; the streak measured 2.5 %. Activity words still come only from real engine events. See [design/08-working-animation-proposal.md](design/08-working-animation-proposal.md).
36. Recorded 3 October 2026: add Ubuntu support to the current native app and verify it on the Ubuntu devbox. This expands item 30's platform scope without changing the Mac and Windows commitments. Broader Linux distribution support, system accessibility and packaging remain separate proof requirements. See [Ubuntu setup](ubuntu.md).
37. Recorded 3 October 2026: Bukno moves to an unmodified T3 server as its backend while keeping the native Rust frontend, following the stages in the [T3 backend plan](t3-backend-audit.md). Stage 1 is a read-only T3 client: pair with the existing Ubuntu server, show its projects, chats and models, and follow live updates without sending anything. The Claude bridge (Pass 2), Bukno's own delegation engine and the remaining direct-Codex failure checks are paused, because T3 replaces them. The direct Codex path keeps working, unchanged, until the full text flow passes through T3 (Stage 2). The backend specification is rewritten only after Stage 2 proves that flow; until then items 3, 10, 12, 14 and 16 describe paused work, not current plans. Stage 1 works from an ordinary local checkout; the `devbox-local` import step from the plan is skipped.

## Proposed, not yet selected

- Local metadata/search storage, lazy transcript loading, and optional viewers.
- Native Windows execution as the initial Windows path; WSL and Linux distributions beyond the checked Ubuntu devbox remain separate scope decisions.
- Initial release targets of Apple Silicon macOS and Windows 11 x64; exact OS minimums, Intel Mac, and Windows ARM64 support still need selection.
- A smaller first-release boundary and implementation contracts, described in the [implementation plan](implementation-plan.md). These are recommendations, not additional agreed features.
- Toolkit, bridge packaging runtime, concurrency defaults, and resource limits in the [first version specification](first-version-specification.md) are starting choices with explicit proof gates. The specification itself is approved (item 31).

## Open proof requirements

- Which supported speech transport works with the existing Codex login? Public source for 0.158.0 and 0.159.2 requires API-key auth for the default WebSocket path; the desktop app also creates calls through its own backend client. Bundling alone does not resolve this.
- Which app-server mode provides draft-only dictation without executing work?
- Does egui (or the fallback toolkit) meet the accessibility and text-input requirements?
- What memory budget is realistic with each engine and its tool children included?
- What exactly happens on quit, engine failure, ambiguous submission, and a second task trying to write the same checkout? The specification defines the intended behavior; it still needs real-engine proof.
- Which revert route works for each engine install method (Claude native installer, npm, Homebrew, Windows installers)?
- How should agents invoke Bukno delegation tools, and how are child results returned, permissions bounded, and workspace ownership transferred? See the [delegation design](implementation-plan.md#5-subagent-delegation-and-handoff).

The [feature map](feature-map.md) contains sources and the wider backlog. Source support is not end-to-end verification.
